# T031 hand-off

artifact-store, wave 2 follow-up F1: the version cap (Q-40, #170) and the event sender with a 5 s deadline off the
handler pool (Q-42, #171). Both are the project owner's decisions of 2026-11-27. No contract change, no new package
(`pyproject.toml` and `uv.lock` untouched).

## Q-40: version cap
- `MAX_VERSION = 2**63 - 1` moved to `app/models.py`; `Artifact.version` and the download's `{version}` path
  parameter use `le=MAX_VERSION`. A larger version is 422 `validation_failed`, location `path.version`, before the
  404 (an unknown name with a version above the cap is also 422). 2^63-1 itself is 404 when not stored.
- `ArtifactRepo.create` refuses when `max(version)` is already 2^63-1: it raises before adding a row, the existing
  cleanup removes the blob, the sender is never reached; the answer is 500 `internal_error`.
- The old 404-above-the-cap cases in `tests/test_store_api.py` were removed (they are now covered by
  `tests/test_store_version_cap.py`).

## Q-42: event sender (`app/core/events.py`)
- `EventSender.schedule(artifact)` is called by the upload handler after the commit. It counts the event (cap 1000,
  one more is dropped and logged) and hands it to the loop with `call_soon_threadsafe`; it returns at once. Each
  event is its own `asyncio` task (no `BackgroundTasks`, nothing awaits it).
- Deadline 5 s from the hand-off; attempt timeout `min(2 s, time left)` (`asyncio.timeout` around the post, so the
  total is bounded, not per phase); waits 0.5 s then 1 s; no attempt or wait is started past the deadline; then drop
  and log. Same `event_id` on every attempt; retry only on a network error, a timeout or a 5xx.
- One `httpx.AsyncClient` per app, created in `start()` and closed in `close()`, both called by the lifespan.
  `close()` cancels pending sends, waits at most 1 s and logs how many were dropped.
- Injectable: `deadline`, `attempt_timeout`, `waits`, `max_pending`, `sleep`, `transport`. Test hooks:
  `pending()` (number of sends pending) and `wait_idle(timeout)` (blocks until none is pending, no sleeping).
- Existing sender tests (`tests/test_store_events.py`, `tests/conftest.py`) moved to the async sender with the same
  assertions. One change in how a test proves a thing: the "row and blob are committed when the event is sent"
  check now reads through the repo (`find` and the blob file) instead of `client.get`, because the fake dashboard
  now runs on the loop thread and a TestClient call from there would deadlock. It proves the same.

## Measured: GET with the hanging dashboard
80 concurrent uploads (all 201) against a listener that accepts and never answers, then one GET download of a stored
version while the events are pending, real uvicorn on a local port, file SQLite database (3 runs each):
- unfixed: 5.73 s, 4.43 s, 3.45 s (main 3bae7ba; sync client on the handler thread pool)
- fixed: 0.05 s, 0.06 s, 0.05 s

The test asserts the GET stays under 1.0 s and that at least one send is pending before and after it.

## Verified
`uv sync --locked`, ruff check and format, mypy, pytest with coverage (81 passed, 96.77 percent, `fail_under` 85),
the five named Q-42 tests (3 reruns), the three Q-40 tests, `test_openapi_matches_contract`, `check_shared_copy.py`,
a live probe on slot 3 (201, 200, 2^63-1 gives 404, 2^63 gives 422, 500 POST then GET pairs: 0 misses, shutdown
logged the dropped pending events).

## Open questions (rare cases, ignored until the end of wave 3)
- The in-memory SQLite engine (`sqlite://`, `StaticPool`, one shared connection) returned 500s under 80 concurrent
  uploads when I first measured with it; a file database (the default) does not. Tests that need concurrency use a
  file database. Not fixed here.
- An event handed to the loop but not yet spawned when `close()` runs is not counted as dropped in the shutdown
  log (its pending count is released when the loop stops).
