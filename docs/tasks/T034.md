## pipeline-runner: baseline and how it is compared (a choice for the reviewer)
The spec asks for one baseline and `stopped < baseline + 1.0 s`. With one GET per condition the runner's own
load (80 runs' steps and uploads on its handler threads, wave 3) made a single GET vary from 0.01 s to 2.5 s with
the dashboard running, and one of six trial runs with medians of 3 failed (stopped median 1.22 s against 0.18 s
baseline). The stopped and baseline single values overlap fully, so I read it as the runner's own load, not
the dashboard. So the
case runs 5 bursts per condition (every run of a burst final before the next) and compares **the median of the 5
stopped GETs** with **the slowest of the 5 baseline GETs + 1.0 s**. Without the fix (pre-follow-up code) the
stopped medians are 14 s, so the check still has a 10 s gap. Cost: the case takes about 70 s. If the lead prefers
the literal single-baseline form, it is a two-line change (`RUNNER_ROUNDS = 1`), with the flake rate above.

The artifact names used in the bursts are unique per write (`hang-<service>-<i>`; one pipeline name per run): 80
uploads racing for one name's next version hit a separate artifact-store defect (below), which is not what this test
is about.

## Defect found (not fixed here; for the lead)
**artifact-store: concurrent uploads of one name can answer 500 `internal_error`.** `ArtifactRepo.create`
(`services/artifact-store/app/repos/artifacts.py`) retries the next-version insert `MAX_VERSION_RETRIES = 10` times
on `IntegrityError`, then raises `RuntimeError("could not assign a version")`. With 80 uploads of one name at once,
some lose more than 10 races. Present before the follow-ups too (same code at bdcfca7).
- Repro (slot 6, current main code): start the stack, then 80 concurrent
  `POST /artifacts/race-<k>?build_id=<uuid>` with a 1-byte body, 8 rounds: 3 of 640 answered 500 (rounds 3 and 7);
  the log shows `RuntimeError: could not assign a version`. It happened every time in the first draft of the
  artifact-store q42 case when the thread pool was also slowed.
- Expected: 201 for each (the contract lists no 5xx for an ordinary upload). Actual: an occasional 500.
- Owner: backend-dev (artifact-store). Whether it counts as a rare case (ignored until the end of wave 3) is the
  lead's call. In a pipeline this would show as `artifact upload failed` for a passing build.
