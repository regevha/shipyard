## Round 2: user decisions #119 and #120

User decisions (Nir, 2026-11-26), quoted in the contracts:
- #119: "Pipeline names use the same rule as artifact names (Q-29): letters, digits, . - _; starts with a letter or digit; 1-100 chars; case-sensitive. A bad name is rejected with 422 when the pipeline is created. No slugifying."
- #120: "The fake upload runs after the last step passes and before the build is marked passed. If the upload fails, the build is failed with reason "artifact upload failed". No retries in wave 2."

What changed (only `events.yml`, `api-pipeline-runner.yml`, `api-dashboard.yml`; `errors.yml`, artifact-store
and release-service unchanged; no `x-assumed` marker added or removed):
- #119: `events.yml#/$defs/PipelineName` is now `$ref: "#/$defs/ArtifactName"` (pattern, 1-100, and the
  trailing-newline `not` guard, all shared, so the two rules cannot drift), with the decision quoted, the
  must-reject values listed, and examples `shipyard-api`, `Web_2.1`, `a`, `"0"`. The "open, issue #119" text is
  gone from events.yml and the runner info; the runner info has a "Pipeline names" paragraph citing the decision.
- `POST /runs` 422 is now an inline response (getRun keeps the shared `ValidationFailed`) with examples
  `invalid` (no steps) and `invalid-name` (`body.name`, same message as the store's `invalid-name`). No new error
  code: errors.yml has no `invalid-name` code; the existing `validation_failed` (422) fits, the same code
  artifact-store uses for a bad `{name}`, so errors.yml is unchanged.
- #120: runner info ("Order and upload failure" paragraph and "Calls it makes"), `startRun`, the dashboard
  who-calls-whom rows for `build.finished` and the upload, and build.finished's description now give the order:
  last step passes -> one upload attempt (run still `running`) -> on 201 the run is passed and build.finished
  (passed) is sent; on anything else the run is failed with `failure_reason` `artifact upload failed` and
  build.finished (failed) is sent. No retry. A build with a failed step uploads nothing. Every "open (#120)" is gone.
- Consequence of the order: the run's `finished_at` and build.finished's `occurred_at` are no longer "the last
  run step's `finished_at`" for a build whose steps all passed; they are when the upload ended. Updated in Run
  and BuildFinished.

Representation of a failure with no failed step: a new required, nullable field `failure_reason` in runner
`Run`, events `BuildFinishedData` and dashboard `BuildView`, whose non-null value is the new shared
`events.yml#/$defs/FailureReason` = `enum: [artifact upload failed]`. Each of the three state tables gains one row,
identical in all three: `failed` + `failed_step: null` + `failure_reason: artifact upload failed` + steps =
`PassedRunSteps`; every other row requires `failure_reason: null`. Why: it is the smallest change that keeps the
outcome enum (`passed`/`failed`, Q-13) and the step shape unchanged, follows the existing "required, null = not
set" rule of the dashboard, and one shared enum keeps the three schemas in parity. A free string was rejected
because it would let the three services emit reasons nobody decided; a new outcome value (`upload_failed`)
was rejected because the user said the build "is failed". Step failures keep `failure_reason` null instead of an
invented reason text. All build examples got `failure_reason: null`; new upload-failure examples in
`BuildFinishedData`, `getRun` (200 `upload-failed`) and `BuildView`. `schema_version` of build.finished stays 1
(nothing is implemented against it yet).

Open for the lead:
- "If the upload fails" is read as: one attempt, any result other than 201 (non-201 status, network error,
