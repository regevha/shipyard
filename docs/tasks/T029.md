## Open questions
Both are with the project owner (asked by the lead on 2026-11-27). Neither is decided here, and T033 implements neither
beyond what its spec says.

1. **pipeline-runner's simulated steps and its upload still run on the handler thread pool.** The runner's background
   task runs in a worker thread: the `time.sleep` of each simulated step and the one upload to artifact-store (up to 10 s
   per httpx phase, #132) hold that thread. Under load (for example 80 concurrent runs with the default 0.5 s steps)
   they can still delay unrelated requests to the runner, as the events did in #171. This is outside the 2026-11-27
   decisions: the #171 decision (Q-42) covers the calls to the dashboard ("a deadline on the dashboard's outbound
   calls", read as the senders' calls to `POST /events`), not steps or uploads. T033 therefore tests the runner with
   `PIPELINE_RUNNER_STEP_SECONDS=0` and an artifact-store that refuses at once. Options: fix it in the wave 2
   follow-ups (a new task after T033), or leave it to wave 3, where the queue and real steps change this code anyway.
2. **The write that marks a run failed can itself fail.** T033 marks a run `failed` with `internal error` in a fresh
   session and retries that write up to 3 times. If all three fail (for example the database is gone), the run stays
   `running` and an ERROR is logged. The #167 decision (Q-41) says a crash is a failure and a run stuck `running` is
   a real bug, but it does not say what happens when the database refuses even the failure record. The contract text
   (`api-pipeline-runner.yml` info: a run is never left `running` because of such an error) is stricter than the
   T033 spec here; the reviewer raised this as B1 on T029, and the lead has asked the project owner. Options: accept
   the residual and name it in the contract; keep retrying (in the background, with a limit) until it succeeds; or
   add a startup or read-time check that fails runs stuck `running` (needs a rule for when a run counts as stuck).
