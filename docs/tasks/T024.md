# T024 hand-off: pipeline-runner

Implements `contracts/api-pipeline-runner.yml`. Code: `services/pipeline-runner/app/` (`main.py` with
`create_app()`, `routers/runs.py`, `core/{config,runner,events,timeutil}.py`, `repos/{engine,tables,runs}.py`,
`models.py`). Tables: `services/pipeline-runner/DATA_MODEL.md`.

## Endpoints
- `POST /runs`: validates the definition, creates the run (committed), answers 202 with the Run (all steps
  `pending`), runs the steps in a FastAPI background task. Bad pipeline name, empty steps, duplicate step
  names, unknown fields: 422 `validation_failed`, no run created.
- `GET /runs/{build_id}`: 200 Run; malformed id 422, then unknown id 404.

## Behaviour
- Step `command` exactly `fail` fails (Q-33); the rest are skipped; `build.finished` follows at once, no upload.
- All steps passed: one upload attempt while the run is still `running`:
  `POST {ARTIFACT_STORE_URL}/artifacts/{pipeline_name}?build_id=<id>`, body `fake artifact of build <id>\n`,
  `X-Checksum-SHA256` of the body, `Content-Type: application/octet-stream`. 201 gives `passed`; anything else
  (non-201, network error, any exception, timeout) gives `failed`, `failed_step` null, `failure_reason`
  `artifact upload failed`. No retry. Then `build.finished` (`occurred_at` = run `finished_at`).
- `build.started` is sent when the first step starts (`occurred_at` = that step's `started_at`).
- Event sender follows PLAN.md Conventions (new event_id per event, reused on retries, 3 attempts, 2 s timeout,
  waits 0.5 s and 1 s, retry on network error, timeout or 5xx only, then log and drop, never raises). Events are
  sent from the run's background task after the state is committed, so they never affect a response or outcome.
  A down dashboard delays only the end of the background task (at most about 7.5 s per event), not any response;
  the run's state is already committed when the event is sent.
- A background error that nothing anticipated is logged and the run stays `running` (the contract has no state
  for it).

## Environment variables
| variable | default | meaning |
| --- | --- | --- |
| `PIPELINE_RUNNER_DATABASE_URL` | `sqlite:///<data dir>/pipeline_runner.db` | database |
| `ARTIFACT_STORE_URL` | `http://127.0.0.1:<18001 + 10 x slot>` | set by the start scripts |
| `DASHBOARD_URL` | `http://127.0.0.1:<18003 + 10 x slot>` | set by the start scripts |
| `PIPELINE_RUNNER_UPLOAD_TIMEOUT_SECONDS` | `10` | timeout of the one upload (connect, read, write, pool each) |
| `PIPELINE_RUNNER_STEP_SECONDS` | `0.5` | simulated duration of each step (tests use 0) |

## Upload timeout (#132)
upload timeout: 10 s. Reason: the fake artifact is a few dozen bytes to a local store, so a healthy upload takes
milliseconds; 10 s is far above any healthy answer but bounds how long a dead or hung store keeps a build in
`running` (no retry, so this is the whole cost). Longer than the 2 s event timeout because a store writes a file
and a row. Per httpx semantics the value applies to each phase (connect, read, write, pool), not to the total.
#131 (option (a)): a timeout after the store saved the bytes still leaves a stored artifact for a failed build;
nothing extra is done.

## Step duration
`PIPELINE_RUNNER_STEP_SECONDS` default 0.5 s per step.

## Notes for others
- `create_app(settings, transport, sleep)` exists so tests inject fakes; `app = create_app()` reads the
  environment at startup (lifespan).
- Sizes are not capped beyond the contract (no max for steps, step names or commands): the contract sets none.
